# Experiment Forge Decision Desk Design

## Outcome

Turn the existing Experiment Forge analytics repository into a recruiter-ready, credential-free browser product for making an experiment decision. A first-time user can choose a clearly labelled sample workspace, understand what was assigned and measured, inspect data-quality risks, compare variants, see uncertainty and practical significance, review guardrails and segments, and trace the recommendation back to pipeline-produced evidence.

The product is a decision interface, not a portfolio dashboard. Every displayed number comes from the existing Python/DuckDB pipeline or from a deterministic artifact generated by it. Synthetic data is labelled as synthetic, and the intentionally flawed sample remains visible as a judgment test.

## Architecture

The analytical code remains the source of truth. A new `forge.py web-build` command will generate two deterministic browser payloads:

- `checkout_progress_indicator`: the existing deliberately flawed sample, expected to require investigation because assignment, temporal, and revenue-quality checks fail.
- `search_autocomplete_refresh`: a clean, positive sample generated through the same source/warehouse/analysis path with the quality-injection switches disabled.

Each payload is a JSON export assembled from generated CSVs, DuckDB marts, `QualityAudit`, and `ExperimentAnalysis`. The static browser in `web/` reads `web/data/catalog.json` and the selected experiment payload. This avoids a credentialed runtime while still consuming reproducibly generated pipeline artifacts. The existing Plotly report generator remains intact for the CLI and methodology continuity; the browser uses inline SVG/CSS charts so the primary workflow remains accessible and does not depend on a third-party CDN.

## Decision contract

The browser exposes four plain-language decision states:

| Decision | Meaning |
|---|---|
| `launch` | Quality gates pass, the primary effect is positive, statistically supported, and clears the practical threshold. |
| `stop` | Quality gates pass and the primary effect is statistically supported in the harmful direction. |
| `continue` | Evidence is directionally useful but not yet strong enough for a launch/stop call. |
| `investigate` | A critical data-quality failure means the effect should not drive a product decision. |

The legacy `recommendation` field (`launch`, `hold`, `iterate`) stays in the analysis payload for backwards compatibility. The new decision is derived by the analysis module and shown with its rationale. The primary conversion interval, p-value, adjusted confirmatory p-value, practical threshold, guardrail deltas, segment rows, daily trend, and every quality check are serialized in the payload.

## Browser workflow

1. A landing view explains the decision job and presents sample workspaces with decision, quality status, user count, and one-line takeaway.
2. Selecting a workspace opens a decision brief with a persistent workspace switcher, decision banner, experiment hypothesis, and evidence summary.
3. A metric section compares control and treatment, shows conversion rates, lift, uncertainty, and practical significance in plain language.
4. A quality section lists pass/warn/fail checks, observed values, thresholds, and why failures block a launch call.
5. Guardrails, segment performance, and the time trend provide context without burying the main decision.
6. A methodology drawer shows metric definitions, denominator logic, multiple-testing treatment, data lineage, and limitations.
7. A CSV validation panel accepts a local file, checks documented headers and required fields, reports row/field errors, and makes clear that validation is local-only; it does not imply that uploaded data has been analyzed.

The UI includes loading, empty catalog, invalid payload, and failure states. Keyboard focus, semantic landmarks, visible focus rings, reduced-motion support, and sufficient color contrast are treated as release requirements.

## Files and boundaries

- `analysis/experiment_readout.py`: extend the decision analysis contract and calculate practical-significance and confirmatory-adjustment evidence.
- `data_generation/synthetic_product.py`: add explicit clean/flawed generation controls while preserving the default tests and sample behavior.
- `web_artifacts.py`: compose a stable, JSON-serializable product payload from real pipeline outputs.
- `forge.py`: add the deterministic `web-build` command.
- `web/index.html`, `web/styles.css`, `web/app.js`: static product shell, styling, and browser state/rendering.
- `web/data/`: generated catalog and experiment payloads committed for deployment.
- `tests/test_web_artifacts.py`, `tests/test_web_build.py`: contract and reproducibility coverage.
- `tests/browser/test_decision_desk.py`: Playwright critical-path coverage and screenshot capture.
- `docs/architecture.md`, `docs/data_lineage.md`, `docs/methodology.md`, `docs/limitations.md`, `README.md`: recruiter-facing documentation and operational instructions.

## Verification

The release gate is:

- existing and new Python tests pass;
- `forge.py web-build` succeeds into a clean temporary workspace and produces both payloads;
- generated payload values match direct DuckDB/analysis outputs;
- static browser smoke test opens without console errors, switches workspaces, expands methodology, validates an invalid CSV, and reaches the full decision content;
- screenshots are captured for the landing state, flawed investigation state, and clean decision state;
- production deployment is checked in a clean browser for the same controls and no console/network errors;
- README and docs make synthetic data, lineage, limitations, local setup, deployment, and the public repository link clear.
